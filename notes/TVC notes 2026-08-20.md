# Tatsunoko vs. Capcom: Ultimate All-Stars (STKE08) Reverse-Engineering Notes

**Build:** NTSC-U / `STKE08`
**Status date:** 2026-08-20
**Scope:** Native game code, runtime memory structures, action resolution, combat systems, attack data, character systems, and supporting instrumentation.
**Excluded:** Mission and trial-mode logic.

## 1. Purpose and notation

This document consolidates the current technical map of *Tatsunoko vs. Capcom: Ultimate All-Stars* for the `STKE08` build. It is intended as a handoff and reference for continued decompilation, runtime tracing, patch design, and training-tool development.

Later mappings take precedence over older provisional labels. In particular, fields such as `fighter + 0x44A4`, `fighter + 0x1218`, and `fighter + 0x1228` have accumulated clearer meanings and should not be described using older shorthand.

### Confidence labels

| Label | Meaning |
|---|---|
| **Confirmed** | Proven by static code behavior, repeatable runtime tracing, breakpoint captures, or a native write/read path with a stable result. |
| **Likely** | Strongly supported by call flow and runtime behavior, but the complete function boundary or every bit-level semantic is not yet proven. |
| **Correlated** | Repeatedly associated with a behavior or packet family, but the exact native branch or isolated bit meaning is not yet complete. |
| **Provisional** | Useful working interpretation that still requires an isolated native proof. |
| **Unresolved** | Tracked field, bit, or function with insufficient evidence for a stable name. |

### Address conventions

- `fighter + X` means an offset from the live fighter structure.
- `actor + X` means an offset from a live attack-actor payload.
- Absolute addresses beginning with `0x8...` are Wii virtual addresses in MEM1 unless otherwise noted.
- Absolute addresses beginning with `0x9...` are generally runtime MEM2 addresses and may be session-specific.
- Instrumentation cave addresses under `0x817F....` are project-allocated telemetry storage, not native game globals.
- Generated DolRecomp chunk names are not original game function names. One generated C chunk can contain many native functions.

## 6.5 Direct input writes are not native controller injection

Writing directly to the fighter input packet can make requested bits appear briefly, but the normal update path overwrites them. A measured decay probe showed an injected back value appearing in roughly 0.7 ms and returning toward baseline within the same update window. Repeated writes can cause side effects such as repeated backdashes, but this does not reproduce the natural controller feed.

A reliable injection mechanism therefore has to occur before or inside the canonical controller conversion path, or through a valid command/action resolver route.

# 8. Native action-selection chain

A natural normal action has been traced through the following chain:

```text
0x80049078 calls 0x80048270
0x80048270 reaches 0x80048DB4
0x80048DB4 calls 0x800463E8
0x800463E8 selects among action sources
normal path reaches 0x80046B90
0x80046B90 calls 0x80045D7C
0x80045D7C scans the character normal-rule table
0x80049098 commits the selected action to fighter +0x1E8
```

For a natural Ryu 5A, the action candidate resolves to `0x100` through the rule match, final rule-scan result, and final action commit.

# 9. Action resolver and transition functions

## 9.1 `0x800446F4` through at least `0x80044CB8`

**Proposed name:** `Fighter_ResolveAction`
**Subsystem:** Fighter action selection and result-state handling
**Confidence:** Likely

Important behavior:

- Standard function prologue begins at `0x800446F4`.
- Fighter pointer is retained in `r29`.
- Reads and writes `fighter + 0x60`, `+0x64`, `+0x1E8`, and larger state offsets.
- The gate at `0x800447E8` can return `-2`, causing the caller to use a cached/result-state action route.
- Continuing at `0x800447F4` bypasses the early `-2` return and allows ordinary action resolution to continue.

Key instructions:

```asm
800447D4: lwz     r5, 100(r29)       # fighter + 0x64
800447D8: lwz     r3, 96(r29)        # fighter + 0x60
800447DC: rlwinm. r0, r5, 0, 25, 25
800447E0: oris    r0, r3, 0x0400
800447E4: stw     r0, 96(r29)
800447E8: beq     0x800447F4
800447EC: li      r3, -2
800447F0: b       0x80044CB8
```

Remaining gaps:

- Exact semantic name of the tested `+0x64` bit.
- Complete function boundary and all callers.
- Exact meaning of several larger fields checked after `0x800447F4`.

## 9.5 `0x800491EC` through `0x80049238`

**Proposed name:** `Fighter_UpdateActionFlags`
**Confidence:** Provisional

# 10. Normal input-rule table

## 10.1 `0x80045D7C`

**Proposed name:** `Fighter_SelectNormalActionFromInputRules`
**Confidence:** Confirmed

The function reads the table pointer from `fighter + 0x13E8`.

Key facts:

- Entry size: `0x18` bytes.
- Terminator: signed halfword `-1` at entry `+0x00`.
- A successful row loads its action candidate from `entry + 0x14`.
- The function continues scanning after a successful row.
- The last successful candidate is returned at `0x8004637C`.
- Hadouken does not resolve through this table, confirming that special commands use a separate path.

Core loop:

```asm
80046010: cmpwi   r0, 0              # entry source selector dispatch
...
80046110: lwz     r0, 4(r31)         # entry +0x04
...
800461A0: lwz     r4, 8(r31)         # entry +0x08 required input bits
800461B4: lwz     r4, 0x0C(r31)      # entry +0x0C state requirement A
800461B8: lwz     r5, 0x58(r25)      # fighter state word
800461EC: lwz     r4, 0x10(r31)      # entry +0x10 state requirement B
...
80046324: lwz     r26, 0x14(r31)     # successful action candidate
8004636C: addi    r31, r31, 0x18
80046370: lha     r0, 0(r31)
80046378: bne     0x80046010
8004637C: mr      r3, r26
```

## 10.2 Rule-entry layout

| Entry offset | Current interpretation | Confidence |
|---:|---|---|
| `+0x00` | Signed selector/type and terminator | Confirmed structural, selector vocabulary unresolved |
| `+0x04` | Source-selector data | Provisional |
| `+0x08` | Required normalized input bits | Confirmed |
| `+0x0C` | State requirement A checked against fighter state | Confirmed use, mask vocabulary unresolved |
| `+0x10` | State requirement B | Confirmed use, mask vocabulary unresolved |

# 12. Character action/script table

## 12.1 Core structure

- Fighter field `+0x1E0` points to the character action table, referred to as `chr_tbl`.
- The table label is stored at relative `-0x18` from the current table base in the scanner model.
- Default table length used by the scanner is `0xB04` bytes.
- Default entry count is 705.
- Default sentinel is at relative `0xB00`.
- Default `chr_act` data begins near relative `0xB04`.

# 15. Attack packet and collision resolver

## 15.1 Collision resolver entry

**Address:** `0x8004DFD4`
**Role:** Native collision resolver / contact-processing seed
**Confidence:** Confirmed core role

At entry, the attack packet pointer is in `r4`. The following packet fields are read directly:

| Packet offset | Field | Meaning |
|---:|---|---|
| `+0x1C` | Property A | Attack height, strength, and reaction-property bitfield |
| `+0x20` | Property B | Damage-routing, actor, capture, and contact bitfield |
| `+0x28` | Authored damage | Base damage authored by the attack |

The resolver passes a local copy of the authored damage into the central damage function at `0x801404DC`.

## 15.2 Reaction-word helper

**Address:** `0x8014177C`
**Role:** Converts Property A bits into the native reaction word
**Confidence:** Confirmed

This helper provides direct static evidence for the low bits encoding attack height and strength.

## 15.3 Damage pipeline

```text
Attack packet authored damage
    -> collision resolver at 0x8004DFD4
    -> central damage calculation at 0x801404DC
    -> collision-route modifications such as chip/capture rules
    -> applied damage value
    -> HP subtraction
    -> externally visible HP delta
```

The current native recorder separates:

1. `authored_damage` from packet `+0x28`
2. damage-calculator output
3. applied damage immediately before HP subtraction
4. observed HP loss from the victim's HP change

This distinction is required because a single HP change can contain more than one contact.

# 20. Damage pipeline and coalesced contacts

## 20.1 Authored, calculated, applied, and visible damage are different values

The current map distinguishes four stages:

1. **Authored damage**: packet `+0x28` or actor `+0x8C`.
2. **Damage calculator output**: output of `0x801404DC`.
3. **Applied damage**: post-route value immediately before HP subtraction.
4. **Observed HP loss**: actual current-HP delta in the victim structure.

A recorder that uses only HP delta can misattribute multi-hit attacks because multiple contacts can be applied during one sampled frame.

## 20.2 Coalescing example

A recorded chained 5B contact produced:

```text
Observed HP loss: 2592
last_hit-like value: 1224
Residual: 1368
```

A later clean contact produced 1368 by itself. The 2592 HP delta therefore contained two contacts in the same frame.

A prior capture set contained 64 hit contacts from 28 attacks, with 13 contacts showing this coalescing behavior.

Recommended attribution priority:

1. Native applied-damage capture when available.
2. Native calculator output when it corresponds one-to-one with the contact.
3. Single-contact internal last-hit value.
4. Raw HP delta only when the contact count is known or the ambiguity is explicitly marked.

# 22. Recoverable health and red life

## 22.1 Native fields

| Offset | Meaning |
|---:|---|
| `+0x24` | max HP |
| `+0x28` | current HP |
| `+0x2C` | auxiliary/recoverable ceiling |
| `+0x30` | pending current-HP delta |
| `+0x34` | pending auxiliary-HP delta |
| `+0x38` | heal sync mode |
| `+0x44A0` | point flag |
| `+0x44BC` | Baroque active phase |
| `+0x454C` | Baroque red spent |

Visible recoverable health is:

```text
recoverable = max(0, auxiliary_hp - current_hp)
```

## 22.2 Normal damage conversion

For a normal damage request of `damage`:

```text
auxiliary_loss = floor(damage * 600 / 1000)
red_generated  = damage - auxiliary_loss
current_loss   = damage
```

Approximately 40% of the damage therefore becomes recoverable, with integer truncation occurring in the auxiliary-loss path.

## 22.3 Current-only cost path

A confirmed cost route removes ten percent of maximum HP from current health while preserving nonlethal behavior:

```text
requested = max_hp // 10
current_after = max(1, current_hp - requested)   # while alive
actual_cost = current_hp - current_after
red_generated = actual_cost
```

This is a current-only loss path rather than ordinary damage.

## 22.4 Reserve recovery step

The native reserve recovery request uses float32 behavior equivalent to:

```text
trunc(float32(max_hp) * float32(0.0001))
```

This is 0.01% of maximum HP per native recovery request, subject to float32 rounding and truncation.

# 32. Giant-team and PTX descriptor investigation

The PTX mixed-team issue is best understood as a descriptor/request problem rather than a late package-file problem.

## 32.1 Confirmed chain-level facts

- PTX can be made selectable and PTX itself loads.
- All four selected character IDs survive the character carousel.
- `game00.seq` requests four player contexts.
- A PTX mixed team emits only three `fpack/chr/...` character package requests.
- The missing partner therefore disappears after script-side player-context requests but before or inside the native descriptor/package-request walk.

## 32.2 Current chain model

```text
Character Select
    -> vs.seq
    -> game00.seq
    -> native 0x32/0x09 operation
    -> native 0x11/0x0C operation
    -> descriptor walk / side filter
    -> fpack/chr/... package requests
    -> fighter package loads
```

The labels `native_3209` and `native_110C` are sequence/native-operation shorthand, not recovered original function names or final DOL addresses.

## 32.3 Working descriptor hypothesis

Current best model:

1. `native_3209(index)` allocates or selects a player/descriptor context.
2. `native_110C(context, mode)` finalizes a per-context or per-side state.
3. A later native routine walks active descriptors and emits package requests.
4. On a PTX mixed side, the partner descriptor is either marked inactive, excluded by a side-count value of one, or replaced with a solo/giant sentinel before its `fpack` request is emitted.

This is a likely structural model, not a completed function map.

## 32.4 Two primary failure classes

### Loop truncation

The package-request caller exits after the PTX descriptor and never reaches the partner iteration.

### Descriptor invalidation

The loop reaches the would-be partner entry, but the descriptor is null, inactive, or converted to a solo/giant sentinel and is skipped.

## 32.5 Exact unresolved target

The highest-value missing point is the first native divergence between a normal 2v2 trace and a PTX-mixed trace at the archive-request boundary. The exact descriptor-cull branch has not yet been named or proven.

Test regions such as `0x80044CC0..0x80044D40` have served as signature controls, not as proven giant-cull functions. Region `0x80135440..0x80135540` is only relevant if a live call stack lands there.

# 38. Known failed, incomplete, or misleading approaches

## 38.1 Forced action fields do not equal a natural move launch

Writing action ID, request, echo, visual-controller, or timeline fields can change visible state or hold a partial action state without reproducing the natural resolver, script, animation, collision, cancel, and actor-spawn path.

Forced action results must not be used by themselves as proof of a natural move mapping.

## 38.2 Direct fighter input writes decay

Directly writing the fighter input packet is overwritten by the canonical input update. Such writes are useful for identifying fields, but not as proof of a correct controller-injection path.

## 38.3 Absolute fighter and `chr_tbl` addresses are not stable

MEM2 addresses captured in one match are useful examples only. Dynamic anchors or validated table scans must be used each session.

## 38.4 `+0x1218` is not a universal invulnerability flag

The timer participates in protected phases, but ordinary action-entry templates also write it. Collision protection must be proven with the companion state writes and native resolver behavior.

## 38.5 `+0x1228` is not universal hitstun

It is a secondary reaction timer associated with the `0x300` reaction family. Ordinary resolved hitstun is at `+0x1210`.

## 38.6 `+0x44A4` is not a Baroque-active flag

It is a mutable lane/permission field read by at least the combo-proration helper and Baroque permission logic. Baroque active state is at `+0x44BC`.

## 38.7 Raw HP delta is not always one hit

Multiple contacts can coalesce into one observed HP change. Native applied-damage capture should be preferred when contact-level attribution matters.

## 38.8 Giant mixed-team failure is not proven to be a package-format error

The PTX partner disappears before the fourth package request is emitted. Late archive or visual fixes cannot restore a descriptor that has already been removed from the native walk.

# 41. Research discipline for future updates

1. Keep native code addresses, session-specific runtime addresses, patch addresses, and instrumentation caves in separate categories.
2. Preserve confidence labels when a field has not been isolated.
3. Treat composite Property A and Property B values as complete packet families until their individual branches are code-proven.
4. Prefer contact-level native values over HP delta for damage attribution.
5. Prefer `+0x1210`, `+0x1204`, and `+0x1220` as native stun clocks rather than deriving timing from wall time.
6. Resolve fighter bases dynamically each session.
7. Do not use forced action-state writes as proof of a natural move-launch path.
8. When a later trace contradicts an older label, update the label rather than preserving both as equal interpretations.
9. For giant-team work, compare a normal 2v2 trace and a PTX-mixed trace at the same archive-request boundary before changing unrelated tables.
10. Keep modification behavior documented separately from the underlying native structures it manipulates.
